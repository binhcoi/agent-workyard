# M2 durable execution slice

Status: the first end-to-end vertical slice is verified with a real Codex worker.
M2 still has the operational gaps listed below.

M1 was rechecked before implementation: uncached tests, vet, formatting, contract
inspection and the shipped configuration check against a separate project passed.
No private planning source was copied into this repository.

## Run the slice

Build `go build -o bin/workyard ./cmd/workyard` (use `.exe` on Windows). Have Codex
installed and authenticated using its ordinary configuration. Run the coordinator
in a separate terminal or under an existing process manager, independently of the
supervisor terminal:

```sh
bin/workyard coordinator serve --state /absolute/private/workyard-state --model YOUR_CODEX_MODEL
```

The coordinator owns one App Server process. Each worker gets a separate Codex
thread, coordinator worker identity, conversation identity and attempt. Workers
use the read-only sandbox and `never` approval policy in this first slice. Native
`multi_agent` is disabled in process and thread configuration. Instructions also
forbid delegation; arbitrary external tools/processes are not comprehensively
restricted by that feature flag. Interactive server requests are refused.

From a supervisor terminal, register a project and Assignment. The state directory
and project should be separate. Assignment administration invokes no model:

```sh
bin/workyard assignment put --state /absolute/private/workyard-state --id demo --project /absolute/project --supervisor session-one --objective 'Verify an input file'
```

Create a JSON brief outside the shared configuration bundle. For example:

```json
{
  "Objective": "Read fixture.txt and report its contents accurately.",
  "Constraints": ["Read only. Do not delegate or modify any file."],
  "Inputs": [{"URI": "fixture.txt", "Description": "Input to inspect"}],
  "Acceptance": ["Report the input contents and how they were verified."],
  "AuthorizedActions": ["Read fixture.txt"]
}
```

Submit through the coordinator. Keep the same task ID and identical request when
retrying an uncertain submission. Changing the brief under an existing ID fails.

```sh
bin/workyard task submit --state /absolute/private/workyard-state --id inspect-input --assignment demo --project /absolute/project --brief /absolute/brief.json --bundle /absolute/agent-workyard/configs/default --skill workyard-verify --effort low
```

`--effort low` explicitly selects lighter reasoning instead of inheriting a
harness default. Choose the model and effort appropriate for actual work.
The submit command exits after durable registration. Close that supervisor
terminal while the worker runs. In a fresh terminal:

```sh
bin/workyard task status --state /absolute/private/workyard-state --id inspect-input
bin/workyard task conversation --state /absolute/private/workyard-state --id inspect-input
bin/workyard task result --state /absolute/private/workyard-state --id inspect-input
bin/workyard task events --state /absolute/private/workyard-state --id inspect-input
```

`task list`, `assignment list`, `coordinator resources`, and `coordinator runtime`
provide discovery. The runtime endpoint reports supported operations and limits.
To record a new managing supervisor, repeat `assignment put` with the same
Assignment/project/objective and the new supervisor ID. Coordinator ownership and
worker identity remain unchanged. No extra worker or conversation is created.

`task cancel` cancels queued work immediately. For active work it records intent
and requests a native interrupt. An accepted interrupt is not cancellation
confirmation; the terminal event provides that evidence. Status retains the
cancellation intent even when confirmation is unavailable. `task result` fails
visibly if no result is available. Worker completion leaves supervisor acceptance
pending; it does not integrate or accept changes.

## Durability and recovery

SQLite commits task state and its event atomically. The state includes project,
Assignment ownership/manager, brief and instruction snapshot, attempt, worker,
conversation, opaque native handles, observed usage and structured result. A
second SQLite database holds a process-lifetime exclusive lock. Process death
releases that lock without stale PID detection. The state directory also holds a
private bearer token and loopback endpoint; the control API is local only. Protect
the directory using ordinary filesystem permissions or Windows ACLs.

Preparation and start are separate adapter operations. The coordinator commits
submission before preparation, then the native thread handle and start intent
before requesting a turn. An ambiguous request cannot cause an automatic retry.
Invalid-parameter/method rejections are definite failures. Transport loss,
timeouts and uncertain server errors remain unknown. Native turn completion
provides completed, failed or interrupted state; process exit alone never means
success. All completed native items are journaled as structured evidence; the
worker's final output is constrained to the result/artifact/verification schema.

Stop and restart the coordinator with the same state directory and model/catalog
settings. Stored terminal results and conversations need no native reconciliation.
For incomplete workers, recovery reads the saved thread's latest turn using the
structured history API. It never starts another inference turn. Completed native
history can restore a result missed before a crash. Interrupted, missing or
ambiguous execution remains unknown. Queued work that never reached preparation
can start. Unknown work retains its capacity slot to avoid accidental overbooking.

A supervisor exit leaves the coordinator and runtime running. A coordinator or
runtime crash can interrupt work; uninterrupted execution across those failures
is not claimed. If the runtime disconnects, the coordinator retains inspection
access, marks affected workers unknown, and refuses new execution until restart.
There is no automatic model-driven monitoring or Assignment administration.

## Verification and remaining work

Deterministic tests cover transactional rollback, actual process-crash lock
release and journal recovery, idempotent submission before/after restart,
conflicting duplicate rejection, capacity, queued cancellation, native cancellation
confirmation, conservative ambiguous-start handling, terminal result persistence,
reconciliation without relaunch, authenticated control and separate conversation
retrieval. A subprocess protocol peer exercises the production adapter over real
stdio pipes, including early completion notifications, usage, isolated threads in
one runtime, independently targeted interruption, native rejection and disconnect.
It performs no model inference and is not an additional production adapter.

Real verification used Codex CLI 0.162.1 on Linux with `gpt-6-luna` and explicit
`low` reasoning effort. One worker, one model turn, a minimal temporary bundle,
no skills, no tools and no delegation returned `WORKYARD_OK`. The submitting CLI
process exited before a separate client observed the worker running; later fresh
clients retrieved its completed result and separate conversation. The coordinator
was stopped and restarted with the same state and retained worker/coordinator
identity, conversation, result and usage. An isolated copy of the state representing
a missed completion recovered the result from the real native thread history
without a second inference turn. This models the missing terminal checkpoint;
it is not a live coordinator kill during inference.

Codex reported **14,624 input tokens, 28 output tokens, zero reasoning tokens**, and
zero cached input tokens. Harness context dominates even a tiny task. These are
observed tokens, not a claimed subscription quota percentage or dollar charge.
No live model is called by `go test`, including race tests. Avoid unnecessary
repeated live runs; terminal inspection and history reconciliation need no model.

Checks passed: uncached package tests, `go test -race ./...`, `go vet ./...`, Linux
build, Windows amd64 cross-build, formatting and `git diff --check`. The execution
sandbox used a temporary Go build cache. Tests include an actual store-process
crash, but no model inference. The smoke state stays outside the repository.

Remaining M2 work and verification limits:

- A real kill near inference completion, real cancellation, native failure and
  simultaneous real-thread control were not exercised to conserve quota. Offline
  lifecycle/protocol tests cover these boundaries; the one live run verifies the
  requested survival/retrieval slice and native completed-history recovery.
- Resolve unknown attempts through a deliberate, evidence-based operator action.
  This slice preserves uncertainty and reserves capacity but has no resolution or
  retry command. Prepared-but-not-started conversations are also conservatively
  retained as unknown after restart.
- The initial configurable catalog contains one local Codex resource and a runtime
  concurrency bound. Catalog expansion and resource policy remain later work.
- Windows cross-compilation is a build check; Windows runtime behavior remains
  unverified.

Messaging/continuation, feedback/approval routing, dependencies, coding isolation,
integration and richer resource policies are outside this slice. No M3 feature,
second adapter, remote execution, dashboard or MCP service is implemented.
